# coliday

팀장 에이전트에게 일을 시키고, 팀원(architect / coder / codex-coder / reviewer / verifier)이
일하는 과정을 터미널에서 추적하는 CLI. 역할마다 Claude Code 또는 Codex CLI 를 골라 쓸 수 있다.
Agent SDK 없이 `claude -p` 와 `codex exec` 를 직접 실행한다.

## 쓰기 전에

- [Claude Code](https://claude.com/claude-code) CLI(`claude`)가 설치돼 있고 로그인돼 있어야 한다. 사용량과 비용은 각자의 계정에 청구된다.
- 팀장은 사람의 권한 확인 없이 실행된다 (`--permission-mode auto`, 확인이 필요한 동작은 자동 거부).
  파일을 고치고 명령을 실행하므로 신뢰하는 레포에서만 쓴다.
- Python 3.11 이상. macOS 에서만 테스트했다. Linux 는 확인하지 않았고 Windows 는 지원하지 않는다.
- 팀장과 팀원은 역할마다 Claude 또는 [Codex CLI](https://github.com/openai/codex)(`codex`)로 바꿀 수 있다. `codex` 는 없어도 된다:
  기본 설정에서는 `codex-coder` 만 Codex 를 쓰고, `codex` 가 설치돼 있지 않으면 그 팀원은 Claude 로 실행된다.
  Codex 를 쓰려면 `codex` 가 설치돼 있고 로그인돼 있어야 한다.
- Anthropic 과 무관한 개인 프로젝트다.

## 설치

```bash
git clone https://github.com/h0l1da2/coliday.git
brew install uv            # 처음 한 번
uv tool install --editable ./coliday
```

`uv` 없이 쓰려면 venv 를 만들고 그 안의 실행 파일을 PATH 에 링크한다:

```bash
cd coliday && python3 -m venv .venv && .venv/bin/pip install -e .
mkdir -p ~/.local/bin && ln -s "$PWD/.venv/bin/coliday" ~/.local/bin/coliday   # ~/.local/bin 이 PATH 에 있어야 한다
```

설치한 뒤 작업할 레포에서 `coliday` 를 실행하면 TUI 가 열린다 (`coliday --help` 로 명령 목록).

### 업데이트

```bash
coliday update            # 최신 버전 받기 (받을 것이 있는지만 보려면 --check)
```

clone 한 폴더의 코드를 그대로 쓰므로(editable) 그 폴더에서 `git pull` 을 하는 것과 같다. 의존성이 바뀐 업데이트면 설치도 다시 한다.

- 새 버전이 올라오면 알려 준다: TUI 는 열 때 알림과 제목 줄에, 명령은 출력 끝에 한 줄로 나온다. 하루에 한 번 백그라운드로 확인하고
  (실행을 기다리게 하지 않는다), 받는 것은 `coliday update` 를 실행했을 때만 한다. `COLIDAY_NO_UPDATE_CHECK=1` 로 끈다.
- 열려 있는 TUI 는 닫았다 다시 연다. 실행 중이던 작업은 이전 코드로 끝까지 돌고, 새로 시작하는 작업부터 적용된다.
- 설정과 작업 기록(`~/.coliday`)은 그대로 남는다.
- clone 한 폴더를 직접 고쳤거나 따로 커밋했으면 덮어쓰지 않고 멈춘다. 정리한 뒤 다시 실행한다.
- `coliday update` 가 없는 예전 버전은 처음 한 번만 clone 한 폴더에서 `git pull` 을 한다.
- clone 한 폴더를 옮기거나 지우면 다시 설치한다.

## TUI

터미널에서 인자 없이 `coliday` 를 실행하면 열린다. 열었던 디렉토리가 git 저장소면 프로젝트 목록에 연결되고 선택된다
(하위 폴더에서 열었으면 그 폴더를 품는 가장 가까운 프로젝트가 선택된다).

```text
┌ 프로젝트 · 보는 중: shop-be (새 작업도 여기) ──────────────────────────────┐
│ shop-be  ● 2  ~/work_dir/shop-be                                           │
│ shop-fe  ● 1  ~/work_dir/shop-fe                                           │
│ 기타          목록에 없는 위치의 작업                                      │
└────────────────────────────────────────────────────────────────────────────┘
┌ 작업 목록 · shop-be ──────────────────────────┐┌ 묶음 · #12 의 일 2개 · 📌 고정 ─────────┐
│ ●  12 2분  shop-be 📌 ↳#3 ▣결제 환불 계산 고쳐 ││ ▼ 주문 취소 흐름  · 차례 3 · 채팅 #12 #3 │
│ ✓   9 3분  shop-be ▣결제 배포 스크립트 정리    ││   요약: 주문 취소 API 와 결제 취소 연동… │
│ ✓   3 2일  shop-be 주문 취소 API 만들어 줘     ││                                          │
└ Space 선택 · Delete 삭제 · Ctrl+B 묶음 ────────┘│   ▌나 #12 · 3번째 요청 · 11-27 13:40     │

│ 13:41:10 팀장       coder에게 분배             ││                                          │
│ 13:44:52 coder      Edit OrderList.tsx         ││   ▌나 #3 · 1번째 요청 · 11-25 09:10  (…) │
│                                                ││   ▌주문 취소 API 만들어 줘               │
│     ◆ AI 보고 (14:10:31)                       ││       ◆ AI ✓ 완료 · 팀원 architect · 25분│
│     스냅숏 테스트 3개가 실패해 멈췄습니다 …    ││       취소 API·결제 취소 연동과 테스트… │
│                                                ││ ▶ 로그인 세션 만료  · 차례 2 · 채팅 #12… │

│                                                ││ ⋯ 묶음 메뉴 (Ctrl+B)                     │
│                                                │└ ↑↓ 이동 · Enter 이동/전체 보기 · →← … ──┘
│                                                │┌ 변경 사항 #12 ───────────────────────────┐
│                                                ││ +public Order cancel                     │

 아래 단축키는 Ctrl 키를 누른 채로 입력합니다 (예: Ctrl+N 새 작업)
 N 새 작업  O 프로젝트  G 프로젝트 추가  T 모델  P 팀·프롬프트  Y 타임라인 복사  B 묶음  S 작업 취소  R 작업 삭제  C 종료
```

- 타임라인 아래 입력창이 채팅 입력이다. 어디에 포커스가 있든 글자를 치면 입력창으로 들어가고, Enter 를 누르면
  선택한 작업에 이어서 시킨다 (같은 세션·같은 worktree, 타임라인도 이어진다). 작업이 하나도 없으면 고른 프로젝트에서
  새 작업으로 시작한다. Esc 로 작업 목록으로 돌아간다.
- 작업이 실행 중일 때 보낸 채팅은 대기했다가(타임라인에 ⏳ 로 표시) 지금 실행이 끝나는 대로 같은 세션에 이어서 전달된다.
  여러 개를 보내면 한 번에 묶어서 전달한다. 실행 도중에 끼어드는 것은 아니다. 작업을 취소하면 대기한 요청은 버려진다.
- 글자 키는 채팅에 쓰이므로 단축키는 모두 ctrl 조합이다: `ctrl+n` 새 작업(새 세션·새 worktree), `ctrl+o` 프로젝트 목록,
  `ctrl+g` 프로젝트 추가, `ctrl+t` 모델, `ctrl+p` 팀·프롬프트, `ctrl+f` 결과물 폴더, `ctrl+l` .env 읽기 허용, `ctrl+y` 타임라인 전체 복사 (`space` 로 고른 작업이 있으면 그것들 모두), `ctrl+b` 묶음 (오른쪽 위 묶음 패널로 가서 메뉴), `ctrl+s` 작업 취소, `ctrl+r` 작업 삭제 (작업 목록에서는 `delete` 키도 된다. 지우기 전에 확인한다), `ctrl+c` 종료.
- 처음 열면 늘 프로젝트 목록에 포커스가 간다. 프로젝트가 없으면 제목이 "프로젝트 · 없음 (Ctrl+G 로 추가)" 으로 나오고 테두리가 강조된다.
  ↑/↓ 로 프로젝트를 고르면 작업 목록·타임라인·변경 사항·채팅이 그 프로젝트의 작업만 대상으로 한다. 고른 곳이 새 작업 위치이기도 하다. Enter 를 누르면 작업 목록으로 넘어가고, 작업 목록에서 Enter 를 누르면 채팅 입력으로 간다.
  - 작업이 어느 프로젝트에 속하는지는 작업을 시작한 위치로 정한다: 그 위치를 품는 프로젝트 가운데 가장 가까운 것 (같은 레포의
    하위 폴더를 따로 연결하면 그 폴더에서 시작한 작업은 하위 폴더 프로젝트에 나온다). 파생 작업은 부모와 같은 프로젝트다.
  - 다른 프로젝트로 갔다 돌아오면 그 프로젝트에서 보던 작업이 다시 선택된다. 프로젝트를 바꾸면 `space` 로 고른 작업은 풀린다.
    입력 칸에 쓰던 글은 지우지 않고, 보낼 곳이 바뀌었다고 한 번 알린다.
  - 프로젝트 줄의 `● N` 은 그 프로젝트에서 실행·대기 중인 작업 수다. 다른 프로젝트의 작업이 끝나면 "shop-fe: 작업 #N 완료" 처럼 알린다.
  - **기타**: 목록에 없는 위치에서 실행한 작업(프로젝트를 목록에서 뺐을 때 등)이 있을 때만 맨 아래에 나온다.
    같은 레포의 하위 폴더만 프로젝트로 연결했으면 그 레포의 작업을 모두 훑어 판정하므로, 작업이 생기거나 지워질 때가 아니면 몇 초 늦게 바뀔 수 있다.
    기타를 보는 동안 새 작업 위치는 마지막으로 고른 프로젝트 그대로이고(`ctrl+n`), 채팅으로 새 작업을 시작하거나
    그룹을 만들거나 `ctrl+e`·`ctrl+x` 를 쓸 수는 없다 (고정·이어서 시키기·삭제와 묶음 메뉴는 된다).
  - 파생 작업을 만드는 사이에 다른 프로젝트로 옮겼으면 화면은 그대로 두고 "작업 #N 시작 (#P 에서 파생) — 프로젝트 X" 만 알린다.
- 작업 목록에서 `space` 로 작업을 여러 개 고를 수 있다 (다시 누르면 풀리고, `esc` 는 모두 푼다). 고른 채로 `delete` 나 `ctrl+r` 을 누르면
  무엇을 지우는지 확인한 뒤 한꺼번에 삭제한다. 실행 중인 작업처럼 지울 수 없는 것은 이유를 알리고 남긴다.
- 작업 목록은 평평한 한 목록이다. 고정한 작업이 맨 위에 오고, 그 밖의 작업은 마지막으로 요청한 순서다.
  기존 작업에 이어서 시키면 그 작업이 맨 위로 올라오고, `경과` 도 그 요청 시각부터 센다 (`coliday ls` 도 같다).
  요청 칸 앞에는 다음 표시가 붙는다.
  - `📌` 고정한 작업
  - `↳#P` 파생 작업 (부모 작업 번호 `P`, `coliday ls` 의 표기와 같다)
  - `▣이름` 보이는 그룹에 든 작업 (이름이 여덟 자를 넘으면 `…` 로 줄인다)
- 작업(채팅)을 정리하는 방법은 세 가지이고, 화면에서는 다음 이름으로 부른다. 셋은 서로 따로라 한 작업이 셋 모두에 들 수 있다.

  | 이름 | 뜻 | 누가 |
  |---|---|---|
  | **묶음** | 한 가지 **일**. 채팅의 **차례**(내 요청 하나 + 그 요청에 AI 가 한 일과 보고)를 일 단위로 모은 것 (레포 단위) | 모델 (사람이 옮기거나 이름을 바꿀 수 있다) |
  | **그룹** | 프로젝트 안에서 사람이 직접 만든 작업 모음 (`▣이름`) | 사람 (`ctrl+b` 메뉴) |
  | **파생** | 한 작업에서 갈라 시작한 부모·자식 작업 (`↳#P`) | 사람 (파생 작업 만들기) |

  한 채팅에서 여러 가지 일을 했으면 그 채팅의 차례들이 여러 묶음으로 나뉘고, 다른 채팅에서 같은 일을 했으면 그 차례들이 한 묶음에 모인다.
- 작업을 고르면 오른쪽 위에 **묶음** 패널이 나온다. 제목은 `묶음 · #N 의 일 K개` 이고 고정한 작업이면 `· 📌 고정` 이 붙는다. 고른 작업이 없으면 패널을 숨긴다.
  - 고른 채팅의 모든 차례가 어느 묶음엔가 보인다 (차례 하나뿐인 묶음도 보인다). 이 채팅에서 가장 최근에 다룬 일이 위에 오고, 맨 위 묶음만 펼쳐진다.
  - **묶음 제목 줄**: `▼ 이름  · 차례 N · 채팅 #12 #3` (펼침) 또는 `▶ 이름 …` (접힘). 펼친 묶음은 제목 아래 흐린 글씨로 요약(두 줄까지),
    접힌 묶음은 `마지막: …` 으로 마지막에 한 일을 보인다.
  - 펼친 묶음 안에는 차례마다 **내 질문**과 **AI 가 한 일**이 들어 있다. 색이 없는 터미널에서도 기호와 들여쓰기로 구분된다.
    - 내 질문: 줄마다 왼쪽 `▌` 막대, 머리 `나 #12 · 3번째 요청 · 11-27 13:40`, 2칸 들여쓰기. 질문은 3줄까지 (넘으면 `…`).
    - AI 가 한 일: 6칸 들여쓰기, 머리 `◆ AI` + 상태 기호·낱말 (`✓ 완료` / `✗ 실패` / `■ 취소` / `⟳ 실행 중` / `? 보고 없음`) + 일한 팀원·걸린 시간,
      그 아래 모델이 쓴 "이 차례에 한 일" 한 문장 (없으면 보고 앞부분). 2줄까지.
    - 차례 사이에는 빈 줄이 있다. 다른 채팅의 차례는 머리 끝에 `(다른 채팅)`, 지금 목록에 없는 채팅이면 `(프로젝트 X)`·`(기타)`·`(목록 밖)` 이 붙는다.
  - 묶음마다 묶음 전체의 최근 6차례와, 그 밖의 이 채팅 차례를 3개까지 더 보인다. 나머지는 `… 이전 차례 N개 — Enter 로 전체 보기` 한 줄이다.
    한 채팅이 묶음 12개를 넘게 걸치면 나머지는 `… 묶음 N개 더` 로 줄인다.
  - 아직 안 묶인 차례는 **임시 묶음** `◌` 으로 보인다: 실행 중이면 `◌ 분류 중`, 끝났는데 아직 안 묶였으면 `◌ 묶기 전`,
    묶기에 실패했으면 `◌ 묶지 못함` (아래에 `Ctrl+B → 안 묶인 차례 묶기`). 실행 중에 보낸 대기 요청은 `⏳ 대기: …` 로 보인다.
  - 그룹·파생은 패널 아래 접힌 구역 한 줄이다: `▸ 그룹 "결제" (2) · 파생 부모 #3 · 자식 1`. → (또는 Enter) 로 펼치면 예전처럼
    `그룹: 이름 (개수)` 와 구성 작업, `파생` 과 부모(`↑`)·자식(`↓`) 작업 줄이 나온다 (고른 작업 줄은 `▶`, 구역마다 30줄까지, 넘으면 `… 외 N개`).
    부모를 지우면 그 위 작업(조부모)이 부모로 보이고, 위 작업이 없을 때만 `↑ #O (지워짐)` 으로 남는다. 펼친 상태는 다른 작업을 골라도 유지된다.
  - 맨 아래는 늘 `⋯ 묶음 메뉴 (Ctrl+B)` 줄이다. 작업 목록에는 묶음 표시를 붙이지 않는다.
  - 1초마다 다시 읽지만 그린 내용이 같으면 손대지 않는다. 바뀌어 다시 그려도 하이라이트한 줄·스크롤 위치·펼친 상태는 그대로다 (펼친 상태는 TUI 를 닫으면 처음으로).
- 묶음 패널과 변경 사항은 오른쪽을 반씩 나눠 쓰고, 포커스가 있는 쪽이 3배로 커진다 (따로 확대 키는 없다).
- 묶음 패널의 키 (패널에 포커스가 있을 때만. 글자 키는 채팅 입력으로 간다):
  - ↑/↓ 이동. **Enter**(또는 클릭): 묶음 제목 줄·`이전 차례` 줄은 **전체 보기**, 다른 채팅의 차례는 그 채팅으로 이동 (다른 프로젝트면 그 프로젝트로
    옮겨 간다. 최근 100개 밖이라 고를 수 없으면 그렇다고 알린다), 이 채팅의 차례는 펼치기/접기, 그룹·파생 줄은 그 작업으로 이동.
  - **→ / ←**: 묶음·차례·그룹·파생 구역을 펼치거나 접는다. 펼친 차례는 질문 전문(2,000자까지)과 보고 앞부분(25줄까지)을 보인다.
    펼치지 않은 차례에서 ← 를 누르면 그 묶음을 접는다.
  - `ctrl+e`: 그룹 이름 바꾸기. `ctrl+x`: 커서가 있는 그룹 구성 작업을 그룹에서 뺀다. `esc`: 작업 목록으로.
- **전체 보기**는 묶음의 모든 차례를 대화처럼 보여 주는 창이다: 질문 전문(왼쪽 굵은 막대)과 AI 보고 전문(Markdown, 경로 링크 포함).
  최근 20차례부터 보이고 `이전 차례 더 보기` 로 20개씩 더 읽는다. ↑/↓ 로 차례를 옮기고, Enter 로 그 차례의 채팅으로 가고,
  `ctrl+y` 로 전체를 글자로 복사한다 (드래그 복사도 된다). 연 순간의 내용이라 실행 중인 차례가 있으면 닫았다 열어야 갱신된다. `esc` 로 닫는다.
- `ctrl+b` 는 묶음 패널로 포커스를 옮기고 묶음 메뉴를 연다 (↑/↓ 와 Enter, Esc 로 닫기). 선택한 작업이 없으면 "선택된 작업이 없습니다" 라고 알린다.
  메뉴 항목은 다음과 같다.
  - **고정 / 고정 해제**: 고정한 작업은 맨 위에 모인다.
  - **그룹에 넣기 → 기존 그룹 · 새 그룹…**, **그룹에서 빼기**: 한 작업은 그룹 하나에만 들어간다. 그룹은 프로젝트마다 따로다: 그 프로젝트에서만 보이고, 이름은 같은 프로젝트 안에서만
    겹치지 않으면 된다 (겹치면 알리고 만들지 않는다). 프로젝트를 목록에서 빼면 그 그룹은 숨겨지고, 같은 경로를 다시 연결하면 돌아온다.
  - **파생 작업 만들기 (#N 에서)**: 파생이 켜진 새 작업 창을 연다 (아래).
  - **그룹 이름 바꾸기**, **그룹 삭제** (그룹만 지우고 작업은 남는다), **빈 그룹 삭제**.
  - **차례 옮기기 → 다른 묶음·새 묶음… (#N k번째: '요청 앞부분')**: 패널에서 하이라이트한 차례(없으면 이 채팅의 마지막 끝난 차례)를 같은 레포의
    다른 묶음으로 옮기거나 새 묶음을 만들어 떼어 낸다. 잘못 묶인 차례를 바로잡는 방법이다.
  - **이 채팅의 차례 모두 옮기기 → …**: 채팅 전체가 한 가지 일이었을 때 끝난 차례를 한꺼번에 한 묶음으로.
  - **묶음 이름 바꾸기 (이름)**, **묶음 전체 보기 (이름)**: 하이라이트한 묶음(차례면 그 차례의 묶음, 없으면 맨 위 묶음).
  - **안 묶인 차례 자동으로 묶기 (채팅 N · 차례 M · 호출 약 K번)**: 최근 작업 100개 가운데 끝났는데 아직 안 묶인 차례(옛 버전이 채팅 통째로 묶은 차례 포함)를,
    모델 호출 수를 보여 주고 확인을 받은 뒤 백그라운드에서 묶는다 (`coliday topics --sort` 와 같다. 한 번에 최대 60번, TUI 를 닫아도 계속된다).
    그런 차례가 없으면 "안 묶인 차례 없음" 으로 흐리게 나온다.
  - 고정·그룹은 Space 로 고른 작업들에, 고른 것이 없으면 지금 선택한 작업에 적용된다. 파생과 묶음 항목은 Space 선택과 상관없다.
    옮겨서 비게 된 묶음은 사라진다. 묶음 합치기는 없다 (차례 옮기기로 대신한다).
    대상은 메뉴를 연 때 정해진다: 메뉴가 열려 있는 동안 다른 화면에서 그 작업·그룹·묶음을 지웠으면 다른 것에 적용하지 않고 알리기만 한다.
- **묶기**는 작업이 끝날 때마다 그 채팅의 팀장 모델이 한다: 그 실행에서 생긴 아직 안 묶인 차례들(대기 요청이 이어져 여러 개일 수 있다)을
  한 번에 물어, 같은 레포의 기존 묶음에 넣거나 새 묶음(일을 요약한 8~15자 이름)을 만들고, 묶음 요약과 "이 차례에 한 일" 한 문장을 쓴다.
  같은 채팅의 바로 앞 차례 2개를 참고로 함께 주어 "4번도 해 줘" 같은 짧은 요청도 앞 일과 같은 묶음에 들어간다.
  - 도구 없이 묻는 짧은 호출이다 (한 번에 8차례까지, 답을 읽지 못하면 한 번 더 묻는다). 작업 비용에는 더하지 않고, 작업 결과·타임라인에도 남기지 않는다.
    Claude 는 프로젝트 밖 빈 폴더(`~/.coliday/topics`)에서 도구·MCP 없이, Codex 는 읽기 전용으로 `.env` 읽기를 막고 실행한다.
  - 실패하면 그 차례는 묶이지 않은 채로 남는다 (`◌ 묶지 못함`, 이유는 `~/.coliday/jobs/<id>/topic.log`). 메뉴의 "안 묶인 차례 자동으로 묶기" 나
    `coliday topics --sort` 로 나중에 묶는다.
  - 기존 묶음의 이름은 모델이 바꾸지 않는다 (요약만 고쳐 쓴다). 사람이 옮긴 차례와 정한 이름은 모델이 다시 바꾸지 않는다.
  - 옛 버전이 채팅 단위로 묶어 둔 것은 화면을 열 때 차례 단위 묶음으로 옮겨 보인다 (옛 표는 그대로 둔다). 차례가 여럿인 옛 채팅은 통째로 한 묶음에 들어 있으므로
    "안 묶인 차례 자동으로 묶기" 로 일 단위로 나눌 수 있다.
  - 다른 터미널이나 백그라운드에서 묶은 결과는 1초 안에 패널에 반영된다.
- `ctrl+b` 는 tmux 의 기본 접두 키와 겹친다. tmux 안에서는 `ctrl+b` 를 두 번 누르거나 tmux 의 접두 키를 바꾼다.
- 맨 위는 연결된 프로젝트 디렉토리 목록이다. `ctrl+g` 로 디렉토리와 이름(비우면 폴더 이름)을 입력해 추가한다.
  목록에 포커스가 있을 때 `ctrl+e` 로 이름을 바꾸고 `ctrl+x` 로 목록에서 뺀다 (디렉토리와 작업은 그대로).
  작업을 시작한 디렉토리는 자동으로 연결된다.
- 목록에서 ↑/↓ 로 작업을 고르면 타임라인과 diff 가 바뀐다. 1초마다 갱신되고, 실행 중인 작업의 diff 는 2초마다 다시 계산한다.
- 새 작업 창(`ctrl+n`)에는 작업 목록에서 작업을 고른 상태일 때만 "선택한 작업 #N 에서 파생" 체크박스가 나온다 (기본 꺼짐).
  켜면 디렉토리 칸이 잠기고 "worktree 없이" 체크박스가 숨는다: 파생 작업은 부모의 위치와 방식을 따른다 (아래 `run --from`).
  부모 상태를 저장하는 동안(서버면 오래 걸릴 수 있다) "파생 작업을 만드는 중…" 이 뜨고 화면은 계속 쓸 수 있다. 다 만들면 새 작업이 목록 맨 위(고정한 작업 아래)에 `↳#P` 표시로 나오고 선택된다.
- `ctrl+t` 로 기본 에이전트와 팀장·팀원의 에이전트·모델을 바꾼다 (아래 "Claude 와 Codex 골라 쓰기").
- `ctrl+p` 로 팀 구성을 보고 바꾼다. 역할을 고르면 실행에 쓰이는 프롬프트가 아래에 나오고, Enter 로 고치기, `a` 새 팀원,
  `d` 팀에서 빼기, `r` 기본값으로 되돌리기를 한다 (아래 "팀원과 프롬프트 바꾸기").
- 이어서 시킨 작업의 타임라인에는 이전 요청·진행 과정·팀장 보고가 모두 남는다. 마우스 휠이나 PgUp/PgDn(또는 alt+↑/↓)로
  올려 본다. 채팅 입력 중에도 PgUp/PgDn 은 타임라인을 넘긴다.
- 타임라인도 묶음 패널과 같은 기호로 내 질문과 AI 를 구분한다: 내 요청(첫 요청과 이어서 시킨 요청)은 왼쪽 굵은 막대 `▌` 와 `나 · 시각` 머리의 블록,
  팀장 보고는 `◆ AI 보고 (시각)` 머리 아래 4칸 들여쓴 Markdown 이다. 그 사이의 `시각 담당 내용` 줄은 AI 팀이 일한 기록이다.
  `ctrl+y` 로 복사한 글도 `▌나 · …` / `◆ AI 보고 (…)` 머리를 쓴다.
- 선택한 작업이 결과물(사진·영상, 사용자가 확인할 파일)을 남겼을 때만 타임라인 아래에 그 작업의 결과물 폴더 경로와 개수가 한 줄로 나온다 (없으면 줄도 `ctrl+f` 도 숨긴다). 누르면 폴더가 열린다.
- 타임라인 맨 위의 `위치:` 줄을 누르면 작업 폴더가 열린다. 팀장 보고에 적힌 경로 가운데 이 컴퓨터에 실제로 있는 것은 링크가 되고,
  누르면 그 폴더가 열린다 (파일이면 그 파일이 든 폴더. 파일을 실행하거나 앱으로 열지는 않는다). 서버의 프로젝트에서는 서버의 경로는 열 수 없고
  이 컴퓨터의 `~/.coliday` 아래 경로만 링크가 된다.
- 보고에 적힌 경로가 실제로는 없으면(에이전트가 중간 폴더를 빼먹고 적은 경우) 작업 폴더 아래에서 같은 이름을 찾아,
  하나뿐일 때 `(실제 위치: …)` 를 옆에 붙인다.
  그 줄을 클릭하거나 `ctrl+f` 를 누르면 폴더가 Finder 로 열려 사진·영상을 바로 볼 수 있다 (터미널 안에 그리지는 않는다).
  아직 비어 있어도 열 수 있고, 몇 번이든 다시 누를 수 있다.
- 타임라인과 변경 사항은 마우스로 드래그하면 선택한 부분이 바로 클립보드에 복사된다.
- `ctrl+c` 로 TUI 를 닫아도 작업은 백그라운드에서 계속된다. 다른 터미널에서 시킨 작업도 같은 목록에 보인다.

## CLI

```bash
cd ~/work_dir/some-project
coliday run "주문 취소 API 추가"      # 실행하며 진행 상황을 실시간 표시 (Ctrl+C 해도 작업은 계속)
coliday run -d "README 정리"          # 백그라운드로 시작만
coliday continue 3 "테스트도 추가해줘" # 작업 3 에 이어서 시키기 (같은 세션·같은 worktree, -d 가능). 실행 중이면 끝난 뒤 전달
coliday run --from 12 "이어서 결제 테스트 추가"   # 작업 12 의 지금 상태에서 새 작업으로 갈라 시작 (파생 작업, 아래)
coliday project                       # 연결된 프로젝트 디렉토리 목록
coliday project add ~/work_dir/shop --name 쇼핑몰   # 연결 (디렉토리 생략 시 현재 디렉토리, --name 생략 시 폴더 이름)
coliday project rm ~/work_dir/shop    # 목록에서 빼기
coliday model                         # 기본 에이전트와 팀장·팀원의 에이전트·모델 보기
coliday model default codex           # 기본 에이전트 바꾸기 (claude / codex)
coliday model coder claude:sonnet     # 역할 하나만 바꾸기 (--reset 으로 기본을 따르게)
coliday team                          # 팀 구성 보기 (역할별 프롬프트·팀원 추가/빼기는 아래 "팀원과 프롬프트 바꾸기")
coliday prompt                        # 실행에 쓰이는 팀장·팀원 프롬프트 보기 (coliday prompt coder 로 하나만)
coliday ls                            # 작업 목록 (텍스트, 모든 프로젝트). 파생 작업은 요청 앞에 ↳#부모번호
coliday show 3 -f                     # 작업 3 타임라인 따라보기
coliday diff 3                        # 작업 3 이 만든 코드 변경
coliday open 3                        # 작업 3 이 남긴 결과물(스크린샷·영상·확인할 파일) 폴더 열기
coliday topics                        # 묶음 목록: 묶음마다 최근 5차례의 내 질문(▌나)과 AI 가 한 일(◆ AI) (--all 모두, --full 질문 전문)
coliday topics --sort                 # 아직 안 묶인 끝난 차례를 지금 묶기 (--max-calls N: 모델 호출 상한, 기본 60)
coliday cancel 3                      # 취소
coliday rm 3                          # 끝난 작업 삭제: 목록·기록과 worktree·브랜치 (변경이 남아 있으면 --force 필요)
```

`coliday run --from 12 "이어서 결제 테스트 추가"` 는 작업 #12 의 지금 상태(커밋하지 않은 변경 포함)에서 새 worktree·브랜치·세션으로 시작한다.

- 부모의 파일·인덱스·브랜치는 건드리지 않는다. 새 작업의 diff 에는 새 작업이 바꾼 것만 나온다.
- .gitignore 된 파일은 따라오지 않는다.
- 부모가 worktree 없이 실행한 작업이면 같은 디렉토리에서 worktree 없이 실행한다. 부모가 실행 중이어도 된다.
- `-C`, `--no-worktree` 와 함께 쓸 수 없다. .env 읽기 허용은 물려받지 않는다 (필요하면 `--allow-env`).
- 첫 실행 때 팀장에게 부모 요청과 마지막 보고 요약을 알려 준다. 첫 실행 전에 그 부모를 지웠으면 알리지 않는다 (목록에서 옮겨 간 조부모를 대신 알리지 않는다).
- `coliday rm` 으로 부모를 지우면 하위 작업은 지운 작업의 부모 밑으로(없으면 최상위로) 옮기고 그렇게 알려 준다.

- 작업마다 `~/.coliday/worktrees/<repo>-<id>` worktree 와 `coliday/<id>` 브랜치를 만들어 그 안에서 일한다.
  그래서 여러 터미널에서 동시에 시켜도 서로 파일을 덮어쓰지 않는다. 커밋하지 않은 변경은 worktree 에 포함되지 않는다.
- `ctrl+r`(TUI) / `rm` 으로 지운 작업은 목록에서 바로 사라지고 worktree·브랜치·로그도 함께 지워진다. 되돌릴 수 없으니
  남길 변경은 먼저 병합한다. worktree 에 변경이 남아 있으면 한 번 더 확인한다 (CLI 는 `--force`).
- 파생 작업(`run --from`, TUI 의 파생 체크박스)은 부모 worktree 의 지금 변경을 스냅샷 커밋으로 만들고 거기서 새 worktree 를 연다
  (임시 인덱스를 써서 부모의 파일·인덱스·브랜치는 그대로다). 부모를 지워도 자식 작업과 worktree 는 남고, 목록에서는 지운 작업의 부모 밑으로 옮겨진다.
- git 저장소가 아니면 `--no-worktree` 로 현재 디렉토리에서 직접 작업한다 (이때는 동시 작업이 충돌할 수 있다).
- 팀장은 commit/push/merge 를 하지 않는다. 결과는 `diff` 로 확인한 뒤 직접 병합한다.

## 설정

| 환경변수 | 기본값 | 설명 |
| --- | --- | --- |
| `COLIDAY_HOME` | `~/.coliday` | DB, 로그, worktree 위치 |
| `COLIDAY_CLAUDE_BIN` | `claude` | claude 실행 파일 |
| `COLIDAY_PERMISSION_MODE` | `auto` | `claude --permission-mode` 값. 권한 확인이 필요한 동작은 자동 거부된다 |
| `COLIDAY_CODEX_BIN` | `codex` | codex 실행 파일 |
| `COLIDAY_OPEN_BIN` | `open` (macOS) / `xdg-open` | 결과물 폴더를 여는 명령 |
| `COLIDAY_NO_UPDATE_CHECK` | (없음) | 값을 주면 새 버전 확인과 알림을 끈다 |
| `COLIDAY_SSH_BIN` | `ssh` | 서버의 프로젝트에 접속하는 명령 |
| `COLIDAY_MAX_ATTEMPTS` | `5` | 실패한 작업을 처음 포함해 몇 번까지 시도할지 (1 이상의 정수) |

어떤 작업(빌드, 테스트, 재작업 등)이 실패하면 팀원과 팀장은 같은 작업을 최대 `COLIDAY_MAX_ATTEMPTS` 번까지만 시도한다.
방법만 바꿔 같은 목표를 되풀이하는 것(테스트가 안 돌아 옵션·우회 스크립트를 바꿔 가며 다시 돌리기)도 같은 작업으로 센다.
그래도 안 되면 팀원은 멈추고 시도 내용과 마지막 오류를 팀장에게 넘긴다. 팀장은 원인을 직접 찾아, 고칠 수 있으면 한 번만 더 맡기고,
원인을 모르거나 이 작업 안에서 고칠 수 없으면 남은 단계를 이어가지 않고 작업을 끝낸다. 최종 보고 맨 위에 "진행 중단"과 함께
무엇이 왜 안 되는지, 사용자가 해 줄 일을 적는다. 이 값은 팀장·팀원에게 주는 지침에 들어가는 것이라 `coliday prompt` 로 확인할 수 있다
(에이전트가 따르는 규칙이지, 프로그램이 횟수를 세어 강제로 끊는 것은 아니다). 바꾼 값은 다음 실행부터 적용된다.

리뷰 → 재작업 → 재리뷰는 요청 하나에서 재작업 2차례까지만 돈다 (팀장 지시문의 "리뷰 반복 상한").
재리뷰가 새 문제를 찾아도 횟수는 늘지 않고, 마지막 리뷰에서 나온 문제는 재작업하지 않고 최종 보고의 "남은 문제"에 적는다.
[P0]·[P1] 이 남으면 보고 맨 위에 "차단 문제 남음"이라고 쓰고, 이어서 고칠지는 사용자가 정한다.
이 상한은 지시문만이 아니라 coliday 가 직접 센다. 리뷰 담당(역할 이름에 `review` 가 든 팀원, 기본 `reviewer`)은 요청 하나에서
최대 3번(첫 리뷰 + 재리뷰 2번)만 부를 수 있고, 넘는 호출은 실행되지 않고 팀장에게 "남은 문제로 보고하고 끝내라"는 이유와 함께 거절된다.
Claude 팀장은 `--settings` 의 PreToolUse 훅으로(.env 를 허용한 작업에도 건다), Codex 팀장은 팀원 요청을 받는 쪽에서 막는다.
막은 호출이 있으면 타임라인에 "리뷰 반복 상한(3번)에 도달해 …" 이 남는다. 이어서 시킨 요청은 새로 센다.

모델 설정은 `~/.coliday/models.json` 에 저장되고 다음 실행(새 작업·이어서 시키기)부터 적용된다. 실행 중인 작업은 바뀌지 않는다.
팀장은 `run --model` / `continue --model` 로 작업별로 덮어쓸 수 있고 (예: `--model codex`, `--model claude:opus`),
따로 고르지 않았으면 기본 에이전트를 따른다.
모델 이름이 실제로 있는지는 실행할 때 claude / codex 가 확인한다 (틀리면 그 작업이 실패로 표시된다).

### Claude 와 Codex 골라 쓰기

기본 에이전트(`claude` 또는 `codex`)를 하나 고르고, 필요한 역할만 따로 바꾼다. 팀장과 팀원 모두 가능하다.

| 값 | 뜻 |
| --- | --- |
| `claude` / `codex` | 그 에이전트의 기본 모델 |
| `claude:opus` / `codex:gpt-6.1-sol` | 그 에이전트의 특정 모델 |

모델 이름은 모두 소문자로, 띄어쓰기 없이 하이픈으로 쓴다 (`gpt-6.1-sol` ○, `GPT-6.1 Sol` ✗).

```bash
coliday model                             # 현재 설정 보기
coliday model default codex               # 기본 에이전트를 Codex 로: 따로 고르지 않은 역할이 모두 Codex
coliday model lead claude:opus            # 팀장만 Claude 의 opus 로
coliday model reviewer codex:gpt-6.1-sol  # 리뷰어만 Codex 의 특정 모델로
coliday model reviewer --reset            # 그 역할을 다시 기본 에이전트를 따르게
```

TUI 에서는 `ctrl+t` 창 맨 위에서 기본 에이전트를 고르고, 역할마다 에이전트(기본을 따름 / claude / codex)와 모델을 고른다.

- 기본 에이전트가 `claude` 면 팀원 정의에 적힌 Claude 모델(architect·reviewer 는 opus)을 쓰고, `codex-coder` 는 Codex 로 일한다.
  기본 에이전트가 `codex` 면 따로 고르지 않은 역할은 모두 Codex 기본 모델로 일한다.
- Claude 팀장 아래의 Codex 팀원은 `codex exec` 를 대신 실행해 주는 작은 Claude(haiku) 에이전트를 거쳐 일한다.
  coliday 는 작업마다 그 팀원용 실행 파일(`~/.coliday/jobs/<id>/codex/`)을 만들고 그 파일만 권한 검사 없이 실행되게 허용한다
  (`--allowedTools`). 허용하지 않으면 auto 권한 모드가 Codex 실행을 "허가받지 않은 외부 전송"으로 보고 막는다.
  Codex 로 둔 팀원에게는 작업 명세와 저장소 내용이 Codex(OpenAI)로 전달된다.
  이 래퍼는 Bash 로 그 실행 파일(`<파일> <명세>`, 끝날 때까지 기다리는 `<파일> --wait <명세>`), `git status --short`,
  `git diff --stat`, `cat <명세>.done <명세>.out` 만 실행할 수 있고, 그 밖의 명령은 PreToolUse 훅이 막는다.
  실행 파일은 끝날 때 `<명세>.done`(종료 코드)과 `<명세>.out`(답)을 남기므로, 오래 걸려 백그라운드로 넘어가도
  `pgrep`·`sleep` 반복문 없이 끝났는지 안다 (그 반복문은 자기 자신과 팀장의 명령줄에 걸려 끝나지 않는다).
- Codex 팀장은 샌드박스(workspace-write) 안에서 실행되고, 팀원에게는 셸 명령으로 일을 맡긴다. 팀원은 coliday 가 샌드박스 밖에서 실행한다.
- Codex 로 실행하는 역할은 수정 도구(Edit/Write)가 없으면 읽기 전용 샌드박스로 돈다 (architect, reviewer).
  팀원 정의에 `"codex_sandbox": "workspace-write"` 를 두면 쓰기를 허용한다 (verifier 는 빌드 산출물 때문에 기본으로 허용).
- 이 컴퓨터에 `codex` 가 없으면 Codex 로 두었던 팀원은 Claude 로 실행하고 타임라인에 알린다 (Codex 팀장은 대신할 수 없어 시작 전에 알린다).
- Codex 는 비용을 알려 주지 않아, Codex 가 쓴 몫은 작업 비용에 포함되지 않는다.
- 이어서 시킬 때 팀장을 Claude↔Codex 로 바꾸면 이전 대화는 이어지지 않고 새 세션으로 시작한다 (작업 디렉토리는 그대로).

프로젝트별 규칙은 각 레포의 `AGENTS.md` / `CLAUDE.md` 를 따른다.

## .env 파일 읽기 차단

에이전트는 기본으로 `.env` 로 시작하는 파일(`.env`, `.env.local`, `.env.prod` …)을 **읽지 못한다**.
사람이 그 작업에 대해 허용했을 때만 읽을 수 있다. 에이전트나 팀장이 스스로 허용할 수는 없다.

```bash
coliday run "배포 설정 점검" --allow-env          # 이 작업에서만 허용
coliday continue 12 "이어서" --allow-env          # 이번 실행부터 허용 (--deny-env 로 다시 막는다)
```

TUI 에서는 새 작업 창(`ctrl+n`)의 ".env 파일 읽기 허용" 을 켠 작업만 허용된다. 채팅 입력으로 시작한 작업은 항상 막는다.
타임라인 첫 줄에 막았는지 허용했는지가 남는다.

작업 도중에 필요해지면 그 작업에만 허용할 수 있다.

```bash
coliday env 12            # 지금 상태 보기
coliday env 12 allow      # 이 작업(세션)에만 허용. deny 로 다시 막는다
```

- 막힌 작업의 에이전트는 다른 방법으로 내용을 알아내려 하지 않고, `.env` 없이는 더 진행할 수 없으면 멈춘 뒤
  보고 맨 위에 ".env 읽기 허용이 필요합니다" 와 이유를 적는다.
- TUI 에서는 타임라인 아래의 `.env` 줄이 버튼이다: 클릭하거나 `ctrl+l` 을 누르면 선택한 작업에만 허용한다 (허용할 때는 한 번 묻는다).
  에이전트가 허용을 기다리거나 읽으려다 막혔으면 그 줄이 눈에 띄게 바뀐다.
- 허용을 기다리며 멈춘 작업은 허용하면 같은 세션을 허용된 상태로 바로 이어서 실행한다.
- 실행 중에 허용하면 그 실행이 끝날 때 정한다 (실행 중인 에이전트의 권한은 도중에 바꿀 수 없다). 에이전트가 `.env` 가 필요하다고
  멈췄으면 멈췄던 일만 이어서 실행하고, 그렇지 않고 끝났으면 이어서 실행하지 않는다. 끝난 작업을 다시 열어 범위가 넓어지지 않게 하려는 것이다.
  이때 타임라인에 그렇게 남기고(그 실행에서 `.env` 읽기가 막힌 적이 있으면 그것도), 허용은 유지되니 필요하면 이어서 시키면 된다.
- 그 밖의 끝난 작업은 다음에 이어서 시킬 때부터 적용된다.

- Claude 는 읽기 금지 규칙과 Bash 샌드박스를 함께 쓴다. 규칙만으로는 `grep -r` 이나 `python -c "open('.env')"` 로 내용이 나오기 때문이다.
  샌드박스 안에서도 네트워크와 홈·임시 폴더 쓰기는 열어 둔다 (빌드가 돌 수 있게).
- Codex 는 권한 프로필에서 `.env*` 를 읽지 못하게 둔다.
- 막을 수 없는 환경이면 막지 않은 채 돌리지 않고 시작 전에 알린다: `claude` 2.1.325 미만, `codex` 0.171.0 미만(팀장일 때),
  리눅스에 `bubblewrap`·`socat` 이 없을 때. (Codex 팀원은 버전이 낮으면 Claude 로 돌린다.)
- 이 컴퓨터의 파일만 막는다. 서버의 프로젝트(SSH)에서는 서버에 있는 `.env` 를 막지 못한다 (에이전트가 ssh 로 서버의 명령을 실행하기 때문).
- 막는 것은 이름이 `.env` 로 시작하는 파일뿐이다. `application-prod.yml` 같은 다른 비밀 파일은 막지 않는다. `.env.example` 도 함께 막힌다.
- 샌드박스 밖에서 이미 돌고 있던 프로세스(예: 먼저 떠 있던 Gradle 데몬)가 읽는 것까지는 막지 못한다.

## 서버의 프로젝트 (SSH)

프로젝트를 이 컴퓨터의 디렉토리 대신 SSH 로 접속하는 서버의 디렉토리로 연결할 수 있다. 디렉토리 자리에 `user@host:/경로` 를 쓴다.

```bash
coliday project add dev@build-server:/srv/shop --name "운영 서버"
coliday project add dev@build-server:/srv/shop --port 2222         # 포트가 22 가 아닐 때 (dev@build-server:2222:/srv/shop 과 같다)
coliday project add myserver:~/work/shop                          # ~/.ssh/config 의 Host 별칭, ~ 는 서버의 홈
coliday run "주문 취소 API 추가" -C dev@build-server:/srv/shop
```

TUI 에서는 `ctrl+g` 창 맨 위에서 "이 컴퓨터의 폴더" 대신 "SSH 로 접속하는 서버의 폴더"를 고른다. 그러면 서버(`dev@build-server`),
포트(비우면 22), 서버의 폴더, 비밀번호 칸이 나온다.

에이전트(`claude`, `codex`)는 **이 컴퓨터에서** 실행되고, SSH 로 서버의 파일을 읽고 고치고 명령을 실행한다.
빌드·테스트·서비스 확인은 서버에서 돈다. 작업 목록·타임라인·diff·이어서 시키기·취소·삭제는 로컬 프로젝트와 같다.

- 서버에는 아무것도 설치하지 않는다 (`claude`·`codex`·coliday 모두 필요 없다. git 저장소면 `git` 만). 로그인도 이 컴퓨터의 것을 그대로 쓴다.
- 에이전트는 작업마다 만들어 주는 실행 파일 세 개로 서버를 다룬다 (`~/.coliday/jobs/<id>/server/`):
  `server '<명령>'`(서버의 프로젝트 폴더에서 실행), `server-pull <경로>`(파일을 이 컴퓨터의 작업 폴더 `jobs/<id>/work` 로 가져오기),
  `server-push <경로>`(고친 파일을 서버에 올리기). 이 파일들만 권한 검사와 샌드박스를 거치지 않고 실행된다.
- 팀장과 팀원 모두 Claude·Codex 어느 쪽으로든 둘 수 있다 (로컬 프로젝트와 같다).
- **서버의 `.env` 는 막지 못한다**: 에이전트가 서버에서 명령을 실행할 수 있어서 서버의 어떤 파일이든 읽을 수 있다 (접속 계정의 권한 안에서).
  이 컴퓨터의 `.env` 는 로컬 프로젝트와 똑같이 막는다.
- 에이전트는 접속 계정의 권한으로 서버에서 무엇이든 실행할 수 있다. 권한이 좁은 계정으로 접속하는 편이 안전하다.
- 키 인증으로 접속돼야 한다. 백그라운드에서 실행하므로 비밀번호나 호스트 키 확인을 물을 수 없다.
  먼저 터미널에서 `ssh dev@build-server` 가 아무것도 묻지 않고 되는지 확인한다. 포트·키·점프 호스트는 `~/.ssh/config` 를 따른다.
- 키 인증이 안 돼 있으면 프로젝트를 추가할 때 서버 비밀번호를 준다: TUI 는 `ctrl+g` 창에서 SSH 를 고르면 나오는 비밀번호 칸, CLI 는
  `coliday project add dev@build-server:/srv/shop --password` (비밀번호를 물어본다).
  그 비밀번호로 **한 번만** 접속해 이 컴퓨터의 SSH 공개키를 서버의 `~/.ssh/authorized_keys` 에 등록하고, 그 뒤로는 키로 접속한다.
  비밀번호는 저장하지 않는다. 이 컴퓨터에 SSH 키가 없으면 `~/.ssh/id_ed25519` 를 새로 만든다 (암호 없음).
  이미 키로 접속되는 서버면 아무것도 바꾸지 않는다. 처음 접속하는 서버의 호스트 키는 이때 묻지 않고 받아들인다.
- worktree 는 서버의 `~/.coliday/worktrees/<레포>-<id>` 에, 브랜치 `coliday/<id>` 로 만든다. git 저장소가 아닌 폴더(배포 폴더 등)는
  물어본 뒤 그 폴더에서 직접 작업한다. 결과물(스크린샷·영상)은 이 컴퓨터의 `~/.coliday/jobs/<id>/artifacts` 에 쌓인다.
- 실행 중에 연결이 끊기면 에이전트의 서버 명령이 실패한다 (에이전트 자체는 이 컴퓨터에서 계속 돈다). 취소하면 이 컴퓨터의
  에이전트는 바로 멈추지만, 그때 서버에서 돌던 명령은 끝날 때까지 남을 수 있다.
- 여러 컴퓨터가 같은 서버의 같은 레포에 작업을 만들면 작업 번호(브랜치 이름)가 겹쳐 worktree 생성이 실패할 수 있다.

## 팀원과 프롬프트 바꾸기

역할마다 설명·프롬프트·도구를 고치고, 새 팀원을 넣거나 기본 팀원을 뺄 수 있다. 팀장 지시문도 바꿀 수 있다.
바꾼 것만 `~/.coliday/team.json` 에 저장되고 나머지는 기본값(`src/coliday/team.py` 의 `DEFAULT_AGENTS`)을 따른다.
다음 실행(이어서 시키기 포함)부터 적용된다.

```bash
coliday team                                   # 역할과 상태(기본값 / 고침 / 추가함 / 뺌) 보기
coliday team show reviewer                     # 고칠 수 있는 원문을 JSON 으로 보기 (lead 는 팀장 지시문)
coliday team set reviewer --prompt-file r.md   # 프롬프트만 고치기 (--prompt "…" 로 직접, '-' 는 stdin)
coliday team set qa --description "구현이 끝난 뒤 사용자 시나리오를 검수한다" \
    --prompt-file qa.md --tools Read,Grep,Bash # 없는 이름이면 새 팀원 (--tools all 은 모든 도구)
coliday team rm codex-coder                    # 팀에서 빼기
coliday team set lead --prompt-file lead.md    # 팀장 지시문 바꾸기
coliday team reset reviewer                    # 그 역할만 기본값으로 (--all 은 전부)
```

TUI 에서는 `ctrl+p` 창에서 같은 일을 한다.

- 팀장은 팀원의 **설명**을 보고 누구에게 언제 맡길지 정한다. 새 팀원은 설명에 맡을 일과 쓸 시점을 적는다
  (예: "구현이 끝난 뒤 사용자 시나리오를 검수한다"). 팀원 목록은 지시문에 자동으로 들어가므로 팀장 지시문을 따로 고칠 필요는 없다.
- 도구에 `Edit`·`Write` 가 없으면 코드를 고치지 못하는 역할이 된다 (Codex 로 돌 때는 읽기 전용 샌드박스).
- 팀원 프롬프트 뒤에는 재시도 규칙과 결과물 폴더 규칙이 자동으로 붙는다. 팀장 지시문 뒤에도 "리뷰 반복 상한"·"실패한 작업 정리" 규칙과 결과물 폴더 규칙이 자동으로 붙는다
  (지시문을 고쳐 써도 빠지지 않는다. 고쳐 쓴 지시문에 같은 제목의 절이 있으면 그 절은 지금 규칙으로 바뀐다). 실제로 전달되는 전문은 `coliday prompt <역할>` 로 본다.
- 팀장 지시문에서는 `{team}` 자리에 팀원 목록(Codex 팀장이면 맡기는 방법)이, `{max_attempts}` 자리에 최대 시도 횟수가 들어간다.
  `{team}` 을 지워도 팀원 목록은 끝에 붙는다. 기본 지시문의 절차·최종 보고 형식을 지우면 그만큼 팀장의 행동이 달라지니 주의한다.
- 역할의 에이전트·모델은 여기서가 아니라 `coliday model` (`ctrl+t`) 에서 고른다. 새 팀원도 거기에 나온다.

`team.json` 을 직접 고쳐도 된다. 프롬프트는 문자열이나 줄 단위 배열로 쓴다:

```json
{
  "lead": {"prompt": ["너는 개발팀 팀장이다.", "{team}", "같은 일은 {max_attempts}번까지만 시도한다."]},
  "agents": {
    "reviewer": {"prompt": ["너는 보안 리뷰어다.", "인증·권한·입력 검증을 먼저 본다."]},
    "qa": {"description": "구현이 끝난 뒤 사용자 시나리오를 검수한다", "prompt": "너는 QA 다.", "tools": ["Read", "Grep", "Bash"]},
    "codex-coder": null
  }
}
```

기본 역할은 바꿀 항목만 적는다 (`"tools": null` 은 모든 도구). 새 역할은 `description` 과 `prompt` 가 필수다. `null` 은 팀에서 뺀다.
형식이 잘못되면 작업을 시작할 때 이유를 알려 주고 시작하지 않는다.

`~/.coliday/agents.json` (`claude --agents` 형식)이 있으면 기본 팀원 전체를 그 파일로 바꾸고, `team.json` 은 그 위에 얹는다.

## 화면 작업의 결과물

웹 화면·UI 를 만들거나 바꾸는 작업이면 팀원(구현·검증 담당)이 실제로 실행해서 스크린샷(.png)이나 녹화 영상(.webm, .mp4)을
`~/.coliday/jobs/<id>/artifacts/` 에 남기고, 팀장은 최종 보고에 파일 이름과 내용을 적는다.

- 찍는 도구는 프로젝트에 있는 것(Playwright 등)을 쓰고, 없으면 `npx playwright` 처럼 임시로 실행한다 (의존성에 추가하지 않는다).
- 사진과 영상은 하위 폴더 없이 한 폴더에 번호를 붙여 늘어놓는다 (`01-login-page.png`, `02-order-flow.webm`).
  실행이 끝나면 coliday 가 폴더를 정리한다: 하위 폴더에 있던 사진·영상은 맨 위로 꺼내고(`verify/ok.png` → `verify-ok.png`),
  하위 폴더에 있던 나머지 파일(찍는 데 쓴 HTML·스크립트·로그)은 지우지 않고 `_other/` 로 모은다. 맨 위에 둔 파일은 그대로 둔다.
  실행 중에는 팀원이 쓰고 있을 수 있어 정리하지 않는다.
- 화면 작업이 아니어도, 프로젝트에 넣을 파일은 아닌데 사용자가 열어 봐야 하는 파일(보고서·정리 문서·내보낸 데이터 등)을 만들면
  같은 폴더 바로 아래에 두고 보고에 전체 경로를 적는다. 프로젝트에 속하는 파일은 원래 자리에 두고 경로만 적는다.
- 로그인이나 백엔드가 필요해 찍지 못하면 "찍지 못함"과 이유를 보고한다. 그때는 폴더가 비어 있다.
- 이어서 시키면 같은 폴더에 쌓이고, 작업을 삭제하면 결과물도 함께 지워진다. 남길 파일은 먼저 옮긴다.
- 실제로 찍을지는 팀장·팀원이 작업 내용을 보고 판단한다 (지침으로 주는 것이라 `coliday prompt` 에서 볼 수 있다).

## 저장 위치

- `~/.coliday/jobs.db`: 작업·이벤트·고정·그룹·파생·묶음 (SQLite). 묶음은 `bundles`(일: 이름·요약)와 `turn_bundles`(차례 → 묶음,
  사람이 옮겼는지, 이 차례에 한 일 한 문장) 표에 있다. 차례는 따로 저장하지 않고 첫 요청과 이어서 시킨 요청 이벤트로 나눈다.
  옛 버전의 채팅 단위 자동 묶음 표(`topics`·`job_topics`)는 지우지 않고 남겨 두며, 새 버전은 읽어서 옮기기만 한다
  (같은 DB 를 옛 버전 worker·TUI 가 써도 서로의 묶음을 지우지 않는다).
- `~/.coliday/projects.json`: 연결된 프로젝트 디렉토리, `models.json`: 모델 설정, `team.json`: 바꾼 팀원 구성·프롬프트
- `~/.coliday/jobs/<id>/stream.jsonl`: 팀장 원본 이벤트, `stderr.log`, `worker.log`, `artifacts/`(결과물),
  `topic.log`(묶기에 실패했을 때만 그 이유. 패널의 `◌ 묶지 못함` 표시도 이 파일을 본다)
- `~/.coliday/topics.lock`: 묶기를 한 번에 하나씩 하게 하는 잠금, `topics.log`: 백그라운드 묶기(`coliday topics --sort`) 출력,
  `topics/`: 묶기 호출을 실행하는 빈 폴더 (프로젝트의 CLAUDE.md·AGENTS.md 를 읽지 않게)

## 개발

```bash
.venv/bin/python -m pytest -q
```

간헐적인 TUI 테스트를 반복 검증할 때는 결과를 보관할 폴더를 지정한다. 기본 3회, 최대 5회까지 실행하며 각 회차의
stdout, stderr, 실제 pytest 종료 코드와 소요 시간을 고유 실행 폴더에 남긴다. pytest 출력은 화면에 중계하지 않고 로그 파일에
직접 기록하며, 화면에는 회차 시작·종료와 종료 코드·로그 경로만 표시한다. 한 회차가 실패해도 나머지 회차를 실행하고,
하나라도 실패하면 명령도 실패 상태로 끝난다.

```bash
.venv/bin/python scripts/repeat_tui_tests.py /tmp/coliday-tui-runs
.venv/bin/python scripts/repeat_tui_tests.py /tmp/coliday-tui-runs --runs 5
.venv/bin/python scripts/repeat_tui_tests.py /tmp/coliday-tui-runs --runs 3 -- -vv -x tests/test_tui.py
```

생성된 `tui-repeat-*` 폴더에는 전체 결과인 `execution.json`과 `run-01` 같은 회차 폴더가 생긴다. 회차 폴더의
`started.json`은 시작 전에, `result.json`은 pytest가 끝난 뒤에만 기록된다. 실행을 중단하면 해당 pytest 프로세스 그룹을
정리하고 `interrupted.json`과 그때까지 파일에 직접 기록된 로그를 남기며, `result.json`은 생기지 않는다. 화면 출력을 받는
파이프가 닫히거나 가득 차도 회차 실행과 로그·종료 코드 저장 및 취소는 기다리지 않고 계속된다. 이 경우 화면 상태 메시지는
늦게 표시되거나 유실될 수 있다. POSIX에서는 실제 테스트가
끝난 뒤에도 결과 집계까지 짧게 프로세스 그룹 소유권을 유지한다. 마지막 회차는 `execution.json` 최종 저장과 화면 출력 정리 뒤
신호 확인까지 소유권을 유지하므로, 그 경계에서 중단 신호가 오면 완료된 회차의 실제 종료 코드를 보존하면서 남은 손자 프로세스를
정리한다. 정상 완료 경계를 지난 뒤에는 그룹 신호 없이 소유권만 놓으므로 손자 프로세스를 기다리거나 종료하지 않는다.
